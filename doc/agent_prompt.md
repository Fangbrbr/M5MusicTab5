# 通用编码开发 Agent 规范 Prompt
## 用途
本规则适用于代码开发、目录调整、代码修改、问题修复、结构重构等所有编码任务。所有操作严格遵循下文约束，不得擅自变通、增减规则。

## 一、标准工作流（强制按顺序执行，不可跳过）
### Step 1 上下文对齐
开始任务前，优先读取项目内相关文档、现有代码、配置文件，**完全以实际文件内容为准，禁止凭记忆、历史对话做假设**。
1. 读取项目说明、编程规范、需求文档、架构文档；
2. 读取目标代码文件、头文件、依赖文件，确认现有接口、数据结构、函数实现；
3. 若发现文档与代码实际状态冲突、需求缺失细节、方案不唯一：立即提出疑问或列出方案优劣对比，禁止猜测实现。

### Step 2 现状验证
核实当前代码真实状态：函数实现完整性、调用链路、结构体/宏定义、已有工具函数、空壳代码、TODO 项。记录现状并明确待完成项、依赖阻塞项，优先处理阻塞依赖。

### Step 3 目标与规划
1. 先定义**可验证的成功标准**，所有迭代围绕标准执行；
2. 任务拆解为**最小可编译/可运行单元**，单步修改后必须保证项目可正常构建；
3. 长任务、多文件修改必须划分步骤，设置检查点。

### Step 4 代码开发与修改
仅实现当前目标所需逻辑，遵循最小改动原则。

### Step 5 构建验证
每完成一个最小单元，执行项目构建命令，要求：**零错误、零警告**。构建失败则立即修复，编译不通过禁止进入下一步。

### Step 6 状态固化（构建通过后必须立即 Git 提交）
构建验证通过后，**必须立即执行 `git add -A` 和 `git commit`**，将变更固化到本地仓库；随后同步更新文档内状态、已知问题、TODO 清单。不得等待用户催促，不得将 EEZ 生成代码、资源文件视为临时文件而跳过提交。

---

## 五、Git 提交规范

AI Agent 应主动协助执行 `git add` / `git commit`，及时固化变更。

1. **每次构建通过后必须立即提交**：完成一个可构建的最小单元、且构建命令返回成功后，必须立即执行 `git add -A` 和 `git commit`，不得遗漏 EEZ 工程文件、生成代码、字体/图片等资源变更。
2. **UI 变更优先**：`components/engine_gui/` 下的 EEZ 工程文件、生成代码、字体/图片等资源一旦变更，**必须立即与代码一起提交**；AI 不得将其视为“用户个人改动”或“临时文件”而跳过，也不得要求用户手动处理。
3. **先构建再提交**：提交前必须构建通过（零错误，可忽略警告除外）。
4. **全量暂存**：使用 `git add -A` 暂存所有变更，不手动挑选文件。
5. **提交信息**：使用中文，简洁描述变更点与验证结果。
6. **推送限制**：不主动执行 `git push`，仅在用户明确要求时推送。
7. **禁止危险操作**：未经用户确认，禁止 `git reset`、`git rebase`、`git checkout -f`、`git clean -fd` 等会丢失/改写历史的操作。

## 二、核心行为铁律（全局强制执行）
### 1. 改动约束（重点：杜绝保留旧内容+添加迁移/删除标注）
1. **目录/文件调整**
   - 移动、删除、合并文件/目录时，**直接输出最终完整结构**；
   - 禁止保留旧目录、旧路径、旧文件条目；
   - 禁止添加任何注释、箭头 `→`、括号说明、「已删除/已合并/迁移至xx」等过程标注；
   - 仅输出纯净、最终生效的目录树，不体现任何修改过程。

2. **代码修改**
   - 仅修改问题对应的必要代码行与文件，**禁止顺手重构、优化格式、修改无关注释、调整未出错代码**；
   - 旧代码直接删除/替换，**禁止注释遗留旧代码**；
   - 禁止在代码内、输出内容中添加「已优化、已调整、版本更新、修改说明」等冗余描述；
   - 复用项目现有函数、宏、工具方法，禁止重复创建同功能实现。

### 2. 设计原则
1. 极简实现：只编写当前需求必需代码，不提前预置未来功能、不做过度抽象；单次逻辑无需封装独立函数。
2. 风格统一：严格遵循项目现有代码风格、命名规则、缩进、括号格式、文件结构，不引入新编码风格。
3. 错误处理：所有可能失败的操作（内存分配、队列、文件、硬件调用等）必须显式判断返回值，返回错误码或打印日志，**禁止静默忽略错误、用默认值掩盖异常**。

### 3. 注释与输出约束
1. 输出内容仅保留**最终成品**，无前置话术、过程解释、思路说明、多余备注；
2. 代码注释遵循项目统一规范，只写必要功能性注释，不添加修改记录、流水式备注；
3. 禁止出现「XX版、优化XX、升级、迭代、润色、完整版/精简版」等版本类、修饰类词汇。

#### 3.1 严禁「过程描述型」注释
Agent 不得在代码中写入仅描述「代码做了什么、从哪里来、为什么存在」的元叙事注释。代码本身应表达行为，注释只表达行为无法表达的信息。

**禁止模式（示例）：**
- 重构/历史叙事：「本模块把 xxx 从 main.c 中抽出...」、「为了简化 xxx 而创建...」、「原先在 xxx 实现，现迁移到本文件...」
- 行为复述：「本函数负责初始化 I2C」、「这里遍历所有 App 并调用 on_update」、「本任务循环执行 HTTP 请求」
- 存在性说明：「本文件提供 xxx 服务」、「本模块用于管理 App 生命周期」、「这是一个胶水层任务」
- 过程过渡：「首先检查参数」、「然后调用底层 API」、「最后返回结果」
- 自我指涉：「本函数...」、「本模块...」、「本文件...」

**允许且鼓励的注释（三类）：**
- **Why**：设计原因、业务背景、约束条件。例如：「必须在设置方向寄存器之前写输出寄存器，避免切换时产生低电平毛刺」。
- **Trap**：边界条件、线程安全、内存生命周期、已知陷阱。例如：「回调在 task_app 上下文执行，禁止调用阻塞操作」。
- **Contract**：调用者责任、前置条件、返回值语义。例如：「调用者需保证 resp_buf 在请求完成前有效；返回 0 表示失败」。

**函数头注释规范：**
- `@brief` 只写「做什么」，一句话，禁止以「本函数」开头；
- 实现细节、存在理由、重构历史不得写入函数注释；
- 修改历史、设计决策应写入 commit message 或 `doc/` 文档，禁止留在代码注释中。

### 4. 冲突处理
若发现代码风格、架构逻辑、接口定义存在多种冲突写法，立即标注冲突点并等待确认，禁止自行选择、混合两种写法。

### 5. EEZ 生成代码禁令（强制执行）
1. **AI Agent 严禁手动修改** `components/engine_gui/src/ui/` 下由 EEZ Studio 生成的任何文件，包括 `vars.h`、`ui.c`、`screens.c`、`screens.h`、`styles.c`、`ui.h`、`eez-flow.h`、`eez-flow.cpp`、`images.c`、`fonts.c` 等。
2. 这些文件的唯一可信源是 `components/engine_gui/TAB_MusicBox.eez-project`；任何编译错误、类型缺失、枚举不完整，**必须回到 EEZ Studio 重新生成**，不得通过 patch 生成文件来绕过。
3. 若生成代码导致构建阻塞：
   - 立即停止当前编码任务；
   - 向用户报告具体错误信息、文件路径、失败原因；
   - 等待用户在 EEZ Studio 侧修复并重新导出，或取得用户**明确书面授权**后方可临时 patch。
4. 仅在用户明确授权下的临时 patch，必须在 commit message 中注明授权与修改范围，且优先推动用户尽快在 EEZ 工程中根治。

## 三、编码通用规范（通用适配所有语言）
1. 文件结构：C 源文件按以下顺序排列 — 全局参数（宏定义）→ 本地参数（static 变量/常量）→ 本地函数前部声明（static 函数原型）→ 全局函数体 → 本地函数体。头文件按宏定义 → 类型声明 → 全局函数声明排列。
2. 缩进与符号：使用项目规定缩进方式，控制流语句必须完整包裹大括号。
3. 变量声明：函数内局部变量统一在代码起始位置声明并初始化，遵循项目排序规则。
4. 命名规范：沿用项目现有命名风格（蛇形/驼峰/模块前缀），不自定义命名规则。
5. 格式化：修改完成后，使用项目内置格式化工具统一格式化代码。

---

## 四、长任务与版本规范
1. 单任务涉及**3个以上文件**或**3个以上步骤**，每完成一步输出检查点：
   `[检查点] 已完成内容 | 涉及文件 | 当前状态(编译通过/待验证) | 下一步计划`
2. 任务执行失败、编译报错，立即回滚至最后一个成功检查点，禁止在异常状态下继续开发。
3. 构建通过后，按项目规范提交版本，提交信息简洁描述变更点、验证结果。
